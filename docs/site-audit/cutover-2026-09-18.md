# Production cutover — 18 September 2026

`www.brianmueller.com` now serves the rebuilt site from Cloudflare. Squarespace is untouched and is
one DNS record away from being restored.

## What is live

| | |
|---|---|
| Hostname | `www.brianmueller.com` |
| Worker | `brianmueller-website`, build command `npm run build:production` |
| Commit | `0a985a0` |
| Apex | `brianmueller.com/*` → `https://www.brianmueller.com/*`, 301, query string preserved |
| Beta | `brianmueller.org` → Worker `brianmueller-website-beta`, `npm run build:beta`, still `noindex` |

## The order it was done in, and why

Each step was chosen so that the thing that could go wrong was not yet reachable by a visitor.

1. **Beta Worker created first**, and `brianmueller.org` moved onto it. This had to come first: with
   both hostnames on one Worker, switching the build command would have made .org an indexable
   duplicate of .com (D-23).
2. **`brianmueller-website` then had no custom domain at all.** The build command was switched to
   `build:production` and deployed into that gap, so the production artifact existed and could be
   checked in full while being reachable only at its `workers.dev` URL.
3. **Zone settings on brianmueller.com** — Always Use HTTPS on; Bot Preference Sync **off** (it
   prepends Cloudflare's own rules to robots.txt, which is what corrupted robots.txt on .org during
   Prompt 07); `brianmueller.com` registered in Web Analytics so the injected beacon reports
   somewhere (D-21).
4. **The Squarespace `www` CNAME was deleted and www attached to the Worker.** This is the cutover.
   Cloudflare refuses a custom domain while an externally-managed record exists, so the delete is
   unavoidable; its original value is in `dns-snapshot-pre-cutover.md`.
5. **Zone cache purged.** The first responses after the switch were cached Squarespace pages
   (`age: 4115`). Worth expecting on any cutover behind a CDN.
6. **Apex redirect rule**, from Cloudflare's own root-to-WWW template, with **Preserve query string
   turned on** — it is off in the template, and the redirect work spent a whole stage establishing
   that query strings must survive.

## One thing that looked like a launch failure and was not

Roughly one request in three returned the old Squarespace page. It would have been easy to call that
a broken cutover. The responses carried `server: Squarespace` and **no `cf-ray` header** — meaning
they never reached Cloudflare at all. The audit environment's outbound proxy does its own DNS, and
the `.com` delegation had not yet propagated, so a share of test requests went straight to
Squarespace. Nothing was wrong with the site.

**The general lesson, for the third time on this project:** before believing a production symptom,
check whether the request reached production. `cf-ray` is the cheap way to tell.

## A second false alarm, from the same cause as the first

An automated run reported 11 of 24 legacy fragments failing on production while the identical test
passed 24/24 against the beta in the same container — which looked like a genuine difference between
the two zones, not a test problem. Things that were checked and ruled out: the served HTML is
byte-identical between .com and .org apart from the beta's `noindex` meta; no Cloudflare injection
(no Rocket Loader, no email obfuscation) on either; the fragment script is present on **30 of 30**
home-page fetches; its CSP hash is in the live header; no CSP violations in the browser; no
`cf-mitigated` challenge header.

The answer came from logging which server answered each failing load: **every failure was
`server: Squarespace` with the old home page and no fragment script; every success was Cloudflare.**
The audit container's outbound proxy was still holding a stale DNS answer and sending a share of
requests to the old site. Same root cause as the "one request in three" scare during the cutover
itself.

**The rule this project has now paid for three times:** before believing a production symptom, prove
the request reached production. `cf-ray` present, or `server:` naming Cloudflare, settles it in one
line — and a control run against a known-good host tells you whether to suspect the site or the
vantage point.
