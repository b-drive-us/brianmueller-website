# Site audit — 18 September 2026

**Subject:** `https://www.brianmueller.com`, live since 18 September 2026
**Commit audited:** `4e9f687` on `main`
**Method:** live site, not the repository, except where stated. Headless Chromium,
390×844 and 1440×900, light and dark, 112 page loads plus targeted probes.
**Purpose:** the input side of the next maintenance release. A second audit by
Codex is being run in parallel; the two get merged before anything is changed.

---

## 0. The version number

**There isn't one.** `package.json` says `0.1.0` — the value `npm init` writes — and
it has never been changed. The repository has **no tags**: 44 commits, no `v1.0.0`,
nothing. The only tag that existed was `_probe`, a leftover from a git-lock
workaround, and it has been deleted.

So the honest answer to "what version is the website?" is: *the site is commit
`4e9f687`, deployed 18 September 2026.* That is a real identifier and it is the one
the deployment actually uses, but it is not a version anyone can say out loud.

Recommendation, and the first item in the release plan: adopt semantic versioning,
tag the current production state **`v1.0.0`** retroactively, and make the
maintenance release **`v1.1.0`**. Costs nothing, and it gives every future
conversation — including the Stripe work — a fixed thing to refer to.

> **Done, 19 September 2026.** `package.json` is `1.0.0`, `v1.0.0` is tagged, and
> `CHANGELOG.md` records what that version is. The version is also stamped into
> every page as `<meta name="version">` and enforced by `check-build.mjs`, so the
> answer is now readable from the site rather than from a deployment log. The
> maintenance release is `1.1.0`.

## 2. Findings

Numbered `M`, continuing from the existing `F`/`N` series so Codex's findings can be
merged without renumbering.

### M01 — The main call to action on `/poems` is almost unreadable · **High**

"Search the whole collection" — the button that sends readers to brianspoems.com,
the archive the page spends three sentences establishing as definitive — renders
**dark brown text on a brown button**.

* Measured: **1.37:1** in light, **1.26:1** in dark. WCAG 2.2 AA needs 4.5:1.
* Visible in the screenshot; this is not a theoretical failure.

**Cause**, and it is a clean one. `base.css:199` sets the button's colour:

```css
.btn{ background:var(--btn-bg); color:var(--btn-fg) }   /* specificity 0,1,0 */
```

but the button sits inside `.archive-note`, and line 285-ish sets:

```css
.archive-note a{ color:var(--ember-deep) }              /* specificity 0,1,1 — wins */
```

`--ember-deep` is the *link* colour, which is a near-match for `--btn-bg`. The
button keeps its background and loses its foreground.

**Scope:** exactly one occurrence site-wide. I measured every `.btn` on all 28 pages
in both themes; nothing else is affected.

**Fix:** narrow the container rule so it cannot reach a button —
`.archive-note a:not(.btn)` — or give `.btn` a matching specificity. One line either
way. Worth shipping on its own if the release slips.

### M02 — The retreat date line fails contrast against the hero photo · **Medium**

`JANUARY 15–17, 2027 · BERGAMO CENTER, OHIO` is gold 11.2px text sitting on the
lighter branches of the hero photograph.

Measured properly — by masking the glyph pixels and reading the background *under*
the letters, not the corners of the bounding box:

| | light | dark |
|---|---|---|
| minimum | 2.68:1 | 3.21:1 |
| median | 4.35:1 | 5.24:1 |
| glyph pixels below 4.5:1 | **53.7%** | **33.1%** |

More than half the text fails in light mode. This is the single most commercially
important line on the site — it is the date of the retreat.

The same treatment on the homepage hero passes comfortably (8.48:1) because the
photo is dark where the text sits. This is specific to the retreat image.

**Fix options:** deepen `.hero-veil`'s gradient at the top, add a text-shadow to
`.hero-eyebrow` as `.hero h1` already has, or use a darker gold on the hero only.

### M03 — No HSTS · **Medium**

`http://` correctly 301s to `https://` at the Cloudflare edge — that part works and
is verified. But no `Strict-Transport-Security` header is sent, so a visitor's
**first** request of the day still goes out in plain HTTP and can be intercepted
before the redirect happens.

This was deliberately deferred (D-12) while the hostname was still moving. The
hostname has now been stable for a fortnight.

**Fix:** ramp it — `max-age=300`, then `86400`, then `31536000; includeSubDomains`
once each step is confirmed. **Do not add `preload`** without a separate decision:
it is effectively irreversible and it would commit every future subdomain of
brianmueller.com to HTTPS forever.

### M04 — A second, indexable copy of the site is public · **Medium**

`https://brianmueller-website.brian-b89.workers.dev` serves the **production**
build: 200, full site, `robots.txt` saying `Allow: /`, and no `X-Robots-Tag`. The
beta Worker correctly sends `noindex`; the production one does not, because for the
custom domain that is exactly right.

The canonical tags do point at `www.brianmueller.com`, which is most of the
protection. But a canonical is a hint, not a directive, and there is no reason for
that hostname to answer at all.

**Fix:** `"workers_dev": false` in `wrangler.jsonc`. One line. Verify afterwards
that the custom domain is unaffected — it is a different route.

### M05 — Astro 5.18.2 carries 3 vulnerable packages; the upgrade is now safe · **Medium**

`npm audit` on the current tree: **1 critical, 1 high, 1 low**.

| Package | Advisory | Reachable here? |
|---|---|---|
| `astro` | critical — XSS in `define:vars` via incomplete `</script>` sanitisation; server-island replay | **No.** `define:vars` is used once, in `LegacyFragments.astro`, and its payload is a hard-coded literal map in the source. No dynamic value ever reaches it. No server islands — this is a static build with no adapter. |
| `sharp` | high — libvips and libheif CVEs | **No.** Nothing uses `astro:assets`; every image is a pre-generated `.webp` in `public/`. `sharp` is in the dependency tree and is never invoked. |
| `esbuild` | low — dev server file read, Windows | **No.** Dev-server-only, Windows-only. |

So this is hygiene, not exposure — and I would rather say that plainly than inflate
it. But the hygiene is worth having, and the blocker has cleared:

**Astro 7.3.3 was tested end to end and the earlier objection no longer applies.**
The Prompt-07 decision (N10 / D-11) rejected the upgrade because 7.3.2 corrupted
prose in fourteen places. On 7.3.3:

* **Rendered text is byte-identical on all 29 pages.** The regression is fixed upstream.

> **Corrected 19 September 2026 — this line was wrong.** The regression is *not*
> fixed in 7.3.3. Astro 7's HTML compressor still eats the whitespace between a
> text node and an adjacent inline element, in **12 places across 7 pages**
> including the contact page and the retreat page. The comparison behind the
> claim above normalised whitespace before diffing, which erases exactly that
> difference — a gate blind to the one bug it was there to catch.
> `tools/compare-build-text.py` finds all 12 and is the correct gate. The
> upgrade shipped in 1.2.0 with `compressHTML: false`, which removes the
> problem entirely at a cost of 142 gzipped bytes per page. See the CHANGELOG.
* **All three CSP `script-src` hashes are unchanged** — the policy needs no edit.
* `npm audit` → **0 across every severity**.
* `check-build.mjs` passes; 29 pages; sitemap and robots identical.

**One condition, and it is not optional.** Astro 7 minifies CSS with Lightning CSS,
which rewrites every width media query to Level 4 range syntax:

```
@media(max-width:640px)   ->   @media (width<=640px)
```

Browsers older than Chrome 104 / Firefox 102 / **Safari 16.4** do not understand
that syntax and **ignore the whole block**. All six of this site's responsive
breakpoints are width queries, so on an older iPhone the mobile layout would simply
stop applying — silently, with nothing in the build to catch it.

Tested fix, which restores the classic syntax exactly:

```js
vite: { build: { cssTarget: ['chrome87', 'edge88', 'firefox78', 'safari14'] } }
```

With that in place the only remaining CSS differences are cosmetic — hex case,
`#FFFFFF`→`#fff`, declaration order, `clamp(a,b,c)`→`max(a,min(b,c))`,
`margin-inline`→`margin-inline-start/end`. All semantically identical, verified rule
by rule. Bundle grows ~2 KB uncompressed. One genuine deletion: Lightning CSS drops
`section{padding-block:clamp(3rem,7vw,5.5rem)}` because the same property is set
again for `section` later in the file — see `M13`. That elimination is correct.

**Recommendation:** upgrade in the maintenance release, with the `cssTarget` line,
and re-run `tools/compare-build-text.py` as the acceptance gate.

### M06 — Nothing checks that the CSP hashes still match the scripts · **Medium**

`script-src` allow-lists three SHA-256 hashes and permits no `unsafe-inline`. That
is the right design. Today it is exactly correct: three hashes allowed, three
distinct inline scripts shipped across 59 occurrences, none missing, none stale
(the 14 `application/ld+json` blocks are data and correctly excluded).

But **`check-build.mjs` never looks at it.** Change one character in the theme
script, or add one entry to the legacy-fragment map, and the hash changes, the CSP
blocks the script, and the build passes. The failure is a console error a visitor
never reports.

This matters more now than it did: Stripe is next, and Stripe Checkout means new
scripts and a new `connect-src`.

**Fix:** extend `check-build.mjs` to recompute the hashes from `dist/` and fail on
any mismatch. `tools/csp-hashes.py` already does the computation; it just needs to
be in the gate rather than run by hand.

### M07 — The site has no icon of any kind · **Low**

`/favicon.ico`, `/favicon.svg`, `/icon.svg`, `/apple-touch-icon.png`,
`/site.webmanifest`, `/manifest.json` — **all 404**. There is no `<link rel="icon">`
in `Base.astro`, no theme-color meta, no web manifest.

Consequences: a blank page icon in every browser tab and bookmark; a grey generic
tile if anyone adds the site to an iPhone home screen; and an automatic 404 on
`/favicon.ico` for every first-time visitor.

**Fix:** an SVG favicon, a 180×180 apple-touch-icon, and a small manifest. The
wordmark treatment (`Brian` in ink, `Mueller` in ember) is the obvious source.

### M08 — Homepage LCP on a slow phone is 3.24 s · **Low**

Measured across all 28 pages at two viewports under a 1.6 Mbps / 150 ms / 4× CPU lab
profile. **Every page except the homepage is comfortably inside the good band** —
most mobile LCPs land between 370 and 480 ms.

| | mobile LCP | desktop LCP | CLS |
|---|---|---|---|
| `/` | **3236 ms** | 808 ms | 0.001 |
| `/retreat` | 1624 ms | 364 ms | 0.000 |
| everything else | 372–476 ms | 168–440 ms | 0.000 |

The homepage LCP element is the hero image. At 390 px and DPR 3 the browser picks
the `1200w` candidate — **133 KB** — because `sizes="100vw"` asks for 1170 device
pixels. The srcset is `800 / 1200 / 1800`.

**Fix options, cheapest first:** add a `500w` or `600w` candidate; or cap with
`sizes="(max-width:40rem) 100vw, 100vw"` plus a DPR-aware ceiling; or re-encode the
existing candidates at a lower quality. Prompt 10 already established that this page
is serialised behind fonts and the hero rather than bandwidth-bound on lazy images,
and that finding still holds — this is the remaining lever.

Same caveat as before: **laboratory, not field.** Once Search Console exists there
will be real CrUX data and it may say this does not matter.

### M09 — `/about` shifts slightly as the fonts load · **Low**

Desktop CLS **0.061** on `/about` — inside the "good" band (<0.1), and the only page
above zero apart from three book pages at 0.002–0.005. The shifts are paragraph
elements moving ~39 px and changing height, which is the signature of a font swap,
not an unsized image.

All five `@font-face` rules use `font-display:swap`, and there is no metric-adjusted
fallback, so text reflows when Newsreader and Archivo arrive. Two of the six files
are preloaded; the italic faces are not.

**Fix if wanted:** a fallback `@font-face` with `size-adjust` / `ascent-override`
matched to Newsreader, so the fallback occupies the same space. Low value, low risk.

### M10 — `/disclaimer` skips a heading level · **Low**

`h1: Disclaimer` → `h3: Interpretation and Definitions` → `h4` → then `h2: General
Disclaimer`. "Interpretation and Definitions" is a peer of the `h2`s and should be
one. WCAG 2.2 1.3.1. Screen-reader users navigating by heading get a false nesting.
Every other page's heading order is correct.

### M11 — Footer links are small targets — but they do pass · **Low**

All eight footer links measure **21 px tall**, below the 24 px of WCAG 2.2 AA 2.5.8.
I expected to report a failure. Measuring the spacing exception instead:

> minimum centre-to-centre distance between any two footer targets: **27 px**

24 px circles centred on each target do not overlap, so **2.5.8 is met via the
spacing exception** — by 3 px. It fails the 44 px of AAA (2.5.5) and Apple's HIG.

Worth noting that `@media (pointer:coarse)` already does exactly the right thing for
the header — `.theme-toggle{min-height:44px}` and `.nav a{padding-block:.55rem}` —
and simply does not cover `.site-foot`. Adding `.site-foot .foot-links a{padding-block:.5rem}`
inside that block would close it. Comfort, not compliance.

### M13 — A dead CSS rule, and the duplicate that causes it · **Low**

`src/styles/base.css` sets `section{padding-block:...}` **twice** — line 110 with
`clamp(3rem,7vw,5.5rem)` and line 482 with `clamp(3.4rem,7.5vw,6rem)`. The later one
wins entirely; line 110 has no effect on anything.

esbuild (Astro 5) ships both. Lightning CSS (Astro 7) removes the first, correctly.
Deleting line 110 makes the source honest regardless of which minifier is in use.

Beyond this the stylesheet is clean: 234 selectors, 9 never matched in any built
page, and 8 of those 9 are state or pseudo-element selectors my checker cannot
evaluate (`::-webkit-scrollbar`, `[data-theme=dark]`, `details[open] summary:after`)
or forward-looking rules for blog content that does not exist yet (`.post-body h2`,
`.post-body a`). Only `.stack-xl` is genuinely unused.

### M16 — `npm run build` produces the *beta* artifact · **Low, but sharp**

`"build": "npm run build:beta"`. Cloudflare Workers Builds is configured to run
`npm run build` then `npm run deploy`-equivalent (`npx wrangler deploy`), and
`wrangler deploy` with no `-c` reads `wrangler.jsonc`, whose name is the
**production** Worker.

`check-build.mjs` validates that an artifact is internally consistent. It cannot
know which Worker the artifact is about to land on. So a beta artifact deployed to
production passes every gate and silently puts `noindex` on all 28 pages.

Today this does not happen: the production Worker's build command was switched to
`npm run build:production` during the cutover, recorded in `cutover-2026-09-18.md`.
(I am taking that from the project's own record, not from the Cloudflare dashboard —
worth a glance when someone is next in there, and note that `STATUS.md` still had the
pre-cutover value, which is part of `M18`.) But the default is pointing the wrong
way, and the `wrangler.beta.jsonc` header already warns about the mirror-image
mistake.

**Fix:** make bare `npm run build` either fail with an instruction, or produce the
production artifact, so the unsafe path requires typing something explicit.

## 6. Flagged, then disproved

Five things this audit raised and then took back after measuring. They are here
because if Codex reports any of them, this is the evidence.

1. **"The homepage hero text has a 1.03:1 contrast ratio."** An artefact of walking
   the DOM for a background colour: the hero text sits on an `<img>`, not on a CSS
   background, so the walk found the page's cream body colour. Re-measured by masking
   the glyph pixels and reading the actual photograph underneath — the h1 is 13.3:1
   at worst and the eyebrow 8.48:1. Both pass comfortably.
2. **"The hero buttons fail contrast."** Same method, different artefact: the first
   measurement took the worst pixel anywhere in the element's box, which is an
   anti-aliased edge blending into a dark photo. Glyph-masked: 16.84:1 and 5.44:1.
   Both pass.
3. **"The skip link stays off-screen when focused."** It does not. I measured it
   during its 0.15 s transition. After the transition it sits at 12 px from the top
   left, 137×45, fully visible.
4. **"The hero has no `srcset` and no `fetchpriority`."** It has both, plus `sizes`
   and explicit dimensions. I had read the `src` attribute alone.
5. **"36 cover images are unreferenced."** They are all referenced — through
   filenames generated from `books.json` slugs, which a literal grep of `src/` cannot
   see. Re-checked against the built output, where the references are real.
